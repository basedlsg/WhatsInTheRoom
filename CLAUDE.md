# What's in the Unlabeled Room?

## Purpose

This repository implements an experiment to understand how vision-language models (VLMs) reason about spatial context in residential architecture. We generate thousands of synthetic floorplans programmatically, render them as images with one unlabeled "mystery" room, and ask NVIDIA VLMs to predict what that room might be. By analyzing predictions across house sizes, regional styles, and room topologies, we can probe the spatial reasoning capabilities and biases of these models.

This is a pure-synthesis experiment: all floorplans are generated by code (no external datasets), all images are rendered programmatically, and all predictions come from real API calls to NVIDIA NIM endpoints.

---

## Experiment Concept

### The Core Question
Can a vision-language model infer the type of an unlabeled room based solely on its spatial relationships, size, position, and connections to labeled rooms?

### The Process
1. **Generate**: Create diverse synthetic floorplans with Python
   - Vary by region (US_suburb, Chinese_city_apartment, European_old_town, etc.)
   - Vary by size (micro, small, medium, large)
   - Use realistic architectural constraints (e.g., bathrooms near bedrooms, kitchens with exterior access)

2. **Render**: Convert floorplans to simple 2D images
   - Draw rooms as rectangles with labels
   - Leave exactly one room unlabeled (the "mystery" room)
   - Show door connections between rooms

3. **Infer**: Send images to NVIDIA VLM with a prompt:
   - "Which room is unlabeled?"
   - "What type of room do you think it is?"
   - "Why? (1-3 sentences)"

4. **Analyze**: Study prediction patterns
   - Do models correctly identify closets vs. bedrooms?
   - Does regional context affect predictions?
   - What spatial cues do models rely on?

## Synthetic Data Generation

All floorplans are generated by code, never hand-written or loaded from external sources.

### Generation Requirements
1. **Parametric**: Use explicit seeds for reproducibility
2. **Diverse**: Stratify across regions and sizes
3. **Realistic**: Follow architectural constraints
   - Bedrooms typically 10-20 m²
   - Kitchens have exterior access (windows or doors)
   - Bathrooms adjacent to bedrooms or hallways
   - Closets adjacent to bedrooms or entryways

4. **Constrained**: Apply region-specific rules
   - US suburbs: Larger rooms, open-plan kitchen/living, 3+ bedrooms
   - Chinese city apartments: Compact, efficient layouts, 1-2 bedrooms
   - European old-town: Irregular shapes, long hallways, fewer bathrooms

### Mystery Room Selection
- Must have at least one door connection (not isolated)
- Should not be the only instance of its type (e.g., don't pick the only bathroom)
- Prefer ambiguous cases (closet vs. office, guest bedroom vs. study)

## Common Tasks

### Add a new region type
1. Define region in `src/core/types.py` (enum)
2. Add region-specific constraints in `src/generation/constraints.py`
3. Update tests in `tests/test_generation.py`

### Add a new room type
1. Add to `RoomType` enum in `src/core/types.py`
2. Define typical dimensions in `src/generation/parameters.py`
3. Update constraint rules if needed

### Change rendering style
1. Edit `src/rendering/image_renderer.py`
2. Run visual regression tests (or manually inspect)
3. Regenerate sample images for documentation

### Debug a floorplan generation issue
1. Find the problematic floorplan by ID
2. Load metadata from `data/floorplans/{id}.json`
3. Extract the `seed` value
4. Reproduce generation with that seed in a test:
   ```python
   floorplan = generate_floorplan(seed=12345, region="US_suburb", size="medium")
   ```

## Architecture Notes & Simplification Opportunities

### Current Implementation

The codebase consists of **~22 Python modules across 7 packages** totaling approximately 5,600 lines of code. For an experimental project, this provides:

**Strengths:**
- Clean separation of concerns
- Easy to extend (add regions, room types)
- Testable components
- Production-ready error handling

**Potential Over-Engineering:**
The current structure may be more elaborate than strictly necessary for a research experiment. Consider these simplification opportunities if the codebase feels too heavy:

1. **Merge storage modules**: `floorplan_store.py`, `image_store.py`, and `results_store.py` could be consolidated into a single `storage.py` module since they're all thin wrappers around file I/O.

2. **Simplify generation package**: The 6-module generation package (`generator.py`, `space_partition.py`, `room_assigner.py`, `door_placer.py`, `constraints.py`, `parameters.py`) could be reduced to 2-3 modules:
   - `generation.py` (main logic)
   - `constraints.py` (parameters + rules)
   Without loss of functionality.

3. **Combine analysis modules**: `aggregation.py`, `metrics.py`, and `visualization.py` could be a single `analysis.py` file.

4. **Rendering**: `image_renderer.py` and `styles.py` could be merged since styles are tightly coupled to rendering.

### Why the Current Structure Exists

The modular structure was chosen to:
- Demonstrate clean architecture patterns
- Make the codebase easy to navigate for future maintainers
- Facilitate testing individual components
- Allow parallel development of different features

### Refactoring Guideline

**If you need to simplify:**
- Start by consolidating the storage layer (easiest, ~200 LOC reduction)
- Keep core models and geometry separate (these are well-abstracted)
- Consider whether you actually need all 6 regional styles or could start with 2-3

**Keep as-is if:**
- You plan to extend the system significantly
- Multiple people will work on the codebase
- You value explicit structure over file count
